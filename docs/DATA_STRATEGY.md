# 数据可信度与多源策略

> Phase 4（数据采集）的施工依据。
>
> 本文回答一个问题：**只用高德会不会不准？要不要多接几个数据源来交叉验证？**
>
> 需求依据：`REQUIREMENTS.md` §6 / §7.3 / §10.3 / §10.4 / §11.4 / §11.6 / §12 / §13.4 / §14

---

## 一、结论

1. **风险真实存在，且需求已预见**（§12.1「同一 POI 的价格和开放时间可能不一致」）。
2. **但需求的解法不是「多接 API」，而是可信度分级**（§11.6「低可信度数据不能直接决定关键决策」）。
3. **多源对不同字段的价值完全不同**：对「客观事实」有用，对「模型计算」无用，对「基准绑定」**有害**。
4. **需要补的数据源只有一类**：官方站点抓取，用于补齐开放时间 / 门票 / 公告。**不需要第二个地图或路线 API。**
5. API 申请清单为空 —— 抓取不需要 Key。

---

## 二、数据源分层

| 层 | 来源 | 负责 | 状态 |
|---|---|---|---|
| **API 层** | 高德 Web 服务 | 地理编码、路线/距离/时间、POI、行政区划、天气、交通态势 | 🟡 **端点已验证，运行时尚未接入**（仅种子脚本在用） |
| **抓取层** | 景区官网 / 博物馆官网 | 门票、开放时间、临时公告 | ⚪ Phase 4 |
| **抓取层** | 城市旅游局 / 政府网站 | 活动、公告、节假日 | ⚪ Phase 4 |
| **降级层** | Mock Data | 缺数据时兜底，**必须明示** | 已用（§6.1 / §10.4 / §14.4） |

策略沿用 §14.1：**API 优先，抓取补充**。

抓取范围受 §6.2（排除「大规模全国实时爬虫」）与 §7.3（先做单城市闭环）约束 ——
实际范围是**北京的一批官方站点**，不是全网爬虫。

## 三、字段清单与来源归属

| 字段 | 主源 | 权威源 | 现状 | 风险 |
|---|---|---|---|---|
| 坐标 | 高德 | 高德（国内唯一正确基准） | ✅ 已入库，GCJ-02 转入 WGS84 | 低 |
| 路线 / 距离 / 通行时间 | 高德 | 高德 | ✅ 已验证 4 种方式 | 低（模型固有误差） |
| POI 名称 / 类别 / 地址 | 高德 | 高德 | ✅ | 中（商业 POI 可能过期、搬迁） |
| **开放时间** | 高德 `opentime2`（自然语言） | **景区 / 博物馆官网** | 🟡 解析器已就绪，靠高德原文 | **高** |
| **门票价格** | 高德 `biz_cost` | **景区官网** | ❌ 实测样本中 `biz_cost` 为空数组 | **高** |
| **是否闭馆 / 临时公告** | — | **景区官网 / 政府公告** | ❌ 无来源 | **高** |
| 天气 | 高德天气 | 高德 / 专业气象 | ❌ **未探测、未接入** | 中（§12.1 存在延迟） |
| 节假日 / 活动 | — | **政府 / 旅游局网站** | ❌ 无来源 | 中 |

**结论：高德提供的是「骨架」（坐标、距离、时间、路线），
而决定「方案能不能照着走」的开放时间与门票，权威源在官网。**
§14.1 原文即写明景区官网的优势是「门票、开放时间、临时公告信息可靠」。

## 四、哪些字段该多源，哪些不该

| 字段类型 | 例子 | 多源交叉验证 | 原因 |
|---|---|---|---|
| **客观事实** | 开放时间、门票、是否闭馆、活动公告 | ✅ **该做** | 存在唯一真值，多源能暴露冲突 |
| **模型计算** | 路线、距离、通行时间 | ❌ **不该做** | 结果不同源于**模型不同**，不是谁更真；取平均会得到两家都不准的数 |
| **基准绑定** | 坐标 | ⚠️ **绝对不该做** | OSM 是 WGS84，高德是 GCJ-02，差 **0.3–0.6 km**，混用引入**系统性**偏移 |

> ⚠️ **禁止用 OSM / 其他 WGS84 数据源「校验」中国境内坐标。**
> 两套基准本身就差 300–600 m，交叉验证的结果是**变差而不是变好**。
> 背景见 [`API_FEASIBILITY.md`](./API_FEASIBILITY.md) 的坐标系章节。

**因此：「多接一个地图 API 做交叉验证」这个方案，对坐标是负收益，对路线是零收益。**

## 五、可信度分级：绑定「源 × 字段」，而不是只绑定源

同一个源对**不同字段**的可信度不同 —— 高德对坐标/路线是高可信，对开放时间/门票是低可信。
所以 `confidence` 必须按 **(来源, 字段)** 记录，不能只按来源打一个总分。

| 层级 | 来源 | 坐标 / 路线 | 开放时间 / 门票 | 说明 |
|---|---|---|---|---|
| **A 官方** | 景区/博物馆官网、政府、旅游局 | — | **0.9 – 1.0** | §11.6「官方数据优先」 |
| **B API** | 高德 | **0.8 – 0.9** | **0.4 – 0.5** | 聚合数据，可能过期 |
| **C 抓取** | 第三方站点 | — | 0.5 – 0.7 | §11.6「API 数据优先于抓取数据」 |
| **D Mock** | 本地样例 | — | 标注为 Mock | 不得冒充真实（§10.4） |

每条关键数据必须带审计链路（§10.3）：`source` / `source_url` / `crawl_time` / `updated_at` / `confidence`。
表结构已预留这些字段。

**已存在的接入点**：`app/planners/scorer.py` 已经把 `confidence` 纳入总分（权重 0.2），
`app/services/candidates.py` 会在 `confidence` 为空时回退为 `0.0` ——
即「未知即可信度最低」，与上表分级方向一致。

## 六、冲突处理与时效

**冲突**：同一字段多源不一致时（§12.1 明确列为风险）——
取权威层级更高的源，**但把冲突记录保留下来**，不静默丢弃（§10.3「所有重要字段必须可回溯」）。

**时效**：`crawl_time` / `updated_at` 超过阈值未更新即降级。

| 字段 | 建议有效期 | 超期处理 |
|---|---|---|
| 开放时间 | 90 天 | 降 confidence |
| 门票价格 | 30 天 | 降 confidence |
| 临时公告 | 7 天 | 视为失效 |

**关键决策的门槛**（落实 §11.6「低可信度数据不能直接决定关键决策」）：

- 开放时间 `confidence` 低于阈值 → 该 POI **不得被自动排进时段安排**，只能标为「待确认」
- 门票价格缺失 → 费用按 **Mock 明示**，不得混入真实数据求和而不标注

已有的解析器 `app/services/opening_hours.py` 已经返回 `confidence` 与 `has_signal`，
可直接作为这里的判定输入。

## 七、降级策略（§12.5 单点故障）

`§12.5` 原文：「地图和 API 服务的故障会影响规划结果」。
这是**唯一真正需要「第二个源」的场景**，但通常用降级而非接第二家 API 解决：

| 级别 | 触发 | 行为 |
|---|---|---|
| 正常 | 高德可用 | 真实距离 / 时间 |
| **缓存降级** | 高德超时或限流 | 使用上次缓存结果，标注 `cached` |
| **几何降级** | 无缓存 | 退回直线距离 × 系数，明确标注 `degraded` |
| **失败** | 城市无数据 | 返回明确错误，不编造方案 |

**任何降级都必须在前端明示** —— 对应 §12.3「若数据不足，输出方案可能看起来合理但不真实」。

## 八、自校验手段（同一源，零额外成本）

不需要引入第二家也能做一致性检查：

1. **逆地理编码回查** —— 把入库坐标转回 GCJ-02 后调 `/v3/geocode/regeo`，
   看返回地址是否指向正确地点。**已用此法验证过全部种子坐标。**
2. **坐标往返** —— `wgs84 → gcj02 → wgs84` 残差应为 0。
3. **开放时间解析自检** —— 解析器返回 `has_signal=false` 时说明原文无有效信息，
   应记为未知而非猜测。
4. **路线一致性** —— 同一 OD 对在驾车/步行之间应有合理量级关系（步行 ≥ 驾车距离）。
