## 1. 项目目标

TravelMind 是面向中国城市旅行的规划辅助系统。用户填写出行条件和个人偏好后，系统结合可获得的景点、开放时间、路线和天气信息，生成可查看、比较和修改的多日行程，减少手工搜索和整理资料的时间。

系统不以生成一篇泛泛攻略为目标，而是使用来源清楚的数据和可解释的规则，给出有时间安排、路线信息、费用估算和不确定性说明的旅行建议。

## 2. 首版范围

### 包含

- 首版验收城市为**福州、北京**：福州作为本地演示城市优先保证数据完整，北京复用现有演示数据；上海作为可选扩展，不纳入首版验收。**每次行程只规划一个目的地城市内的多日旅行**。
- 收集目的地、日期、天数、成人与儿童人数、整单总预算、兴趣、旅行节奏、交通偏好、每日可出行时间、每日最大步行距离，以及餐饮/住宿参考预算。
- 根据景点信息、开放时间、真实路线与每日限制安排游览顺序和时段；路线只用于距离、耗时和交通费用，不做导航。
- 让天气实际影响户外景点的评价、室内景点选择和方案评分；首版使用高德近 4 天预报，超出范围标未知。
- 计算整趟、所有同行人员的总费用，纳入门票、市内交通、餐饮和住宿；区分已确认、估算和未知费用。
- 展示每日行程、按 1→2→3 顺序标注的静态地图、天气、信息来源和需要确认的数据。
- 保存规划方案及历史版本，支持重新打开、改条件后重新生成新版本。
- 对真实数据、估算值和演示数据作清楚区分。

### 暂不包含

- 一趟旅行跨多个目的地城市的城际交通。
- 国际旅行、航班与火车规划。
- 在线订票、预订、支付、实时酒店价格或库存。
- 大规模、全国性通用爬虫；自动发现并抓取全国官网；运行时实时抓取官网。
- 地图导航、交互式 JS 地图、路线拖拽和实时路况。
- 单个景点的锁定、删除或替换；首版只支持改条件后整趟重新规划。
- 行程中的局部调整（延长/缩短单个景点、局部替换、删除单个景点）和“最小变更”优化；首版不实现。
- 第二天气源（首版不接入，保留 WeatherProvider 接口供后续评估）。
- 旅行期间自动监控和动态重规划。
- AI 自然语言规划、对话修改或 AI 生成路线。
- 固定数量的方案、复杂优化算法或自动选择旅行日期。

住宿和餐饮使用城市级参考预算，不承诺实时价格、库存或预订；城际交通不计入总费用。首版不绑定具体酒店，也不建模住宿点到首个景点、最后景点回住宿的接驳，步行/交通只计算相邻景点之间。

### 后续加分项（Phase 2，不纳入首版验收）

- **出行执行清单 / 购票指引**：规划完成后列出景点官方购票/预约渠道、票价、预约窗口、实名要求、开放/闭馆信息和官方链接；住宿给区域与预算，餐饮给区域与预算。
- 只做指引，**不做站内下单、支付、退改、库存或抢票**；不做实时提醒和动态重规划。
- 数据只对每城 5 个重点景点核验官方购票信息，其余标“官方渠道待确认”；不得伪造链接或票价。

福州、北京各准备 15–20 个 POI，每城 5 个重点景点核验官方票价/开放时间；上海作为可选扩展，不占用首版验收时间。

## 3. 输入方式与规划规则

### 用户偏好

- 兴趣类别分别使用 0–100 滑动条，不要求兴趣值总和为 100%。
- 旅行节奏使用 0–100 的“轻松—充实”滑动条，映射到每日条目上限、条目间隔和评分。
- 预算、成人与儿童人数、日期、天数、每日时间和步行上限使用明确且带单位的输入；总预算是**整单、所有同行人员**的预算。
- 交通偏好使用选项（自动 / 步行 / 公交 / 驾车 / 骑行），不用一个滑动条混合表示不同交通方式。
- 餐饮按“人均每日预算”、住宿按“每间每晚预算”输入；默认取城市参考值，用户可覆盖。

滑动条用于表达偏好和调整评分，不允许抵消硬约束违规。

### 硬约束

- 已确认的景点开放时间。
- 每日可出行时间范围。
- 每日最大步行距离（按真实步行路线累计；路线不可用时标未知，不能声称已满足）。
- 同一景点不跨日重复安排，每日条目不超过上限。

违反硬约束的安排不能靠兴趣、天气或其他评分补偿。无法确认的信息应标为未知或待确认，不得假装已核实。

路线调用失败时，该段距离和耗时标为未知，不得用直线距离替代后继续声称满足步行或时间约束；如为排程使用回退耗时，必须明确标注为估算。

### 软目标

- 整趟旅行总预算。
- 兴趣匹配、旅行节奏、交通偏好、路线便利、舒适度和天气适宜性。
- 费用构成：门票、市内交通、餐饮和住宿；每类区分已确认、估算和未知。

预算是**整趟旅行的软约束**：先安排多日行程，再汇总全程预计费用；超预算会降低费用评价并提示差额，但不单独淘汰方案。平均每日预算只能作为参考，不要求每天花费相同。

费用未知不能按 0 元计入：总费用至少展示“已确认 + 估算”，未知项单列；预算差额据此计算，并注明是否完整。

首版只生成 **1 个可行方案**；后续若恢复多方案，数量和分类再由实际可行且质量足够的结果决定，不为凑固定数量展示低质量方案。

### 天气

- 天气是首版规划依据，不能只显示天气而不影响结果。
- 不利天气应降低受天气影响较大的户外景点优先级，并考虑合适的室内候选。
- 天气适宜性进入方案评分。
- 天气缺失或超出可用预报日期范围时，明确标记“暂无可靠预报”，不能猜测，也不能声称已按天气优化。
- 天气信息不能替代开放时间、路线和出行前核实。

首版天气源为高德 Web 服务：按城市 adcode 取实况和预报，实测返回当天+3 天；具体可用日期以接口实际返回为准，不写死天数。保留 `WeatherProvider` 接口，第二天气源留待后续评估，不纳入首版。

### 规划接口契约（v0.2 旧接口 + v0.3 当前实现）

> v0.2 是旧版 `/planner/*` 无状态接口的契约，只覆盖多日规则排程骨架；目标契约 v0.3 单独冻结在 [`API_CONTRACT_V0.3.md`](./API_CONTRACT_V0.3.md)。v0.3 的持久化、路线/天气、门票人数计价、费用三态、版本历史和餐食/住宿选择已落地（`/trips` + `/trips/{id}/plans`）；规范拆表仍未完成。

请求（`POST /api/v1/planner/generate`、`/generate-options`、`/replan`）：

| 字段 | 含义 |
|---|---|
| `city` | 目的地城市名；每次只规划一个城市 |
| `start_date` + `days` | 多日表示：从 `start_date` 起连续 `days` 天，`days` 取 1–30 |
| `interests` | 兴趣类别 → 0–100 滑动条值；进入规划器归一化为 0–1 |
| `budget_total` | 整趟旅行预算，0 表示未设置 |
| `daily_start` / `daily_end` | 每日可出行时间范围，`daily_end` 必须晚于 `daily_start` |
| `max_daily_items` | 每日最多安排的景点数 |
| `avoid_tight_schedule` | 是否放宽条目之间的间隔 |
| `max_walk_km` | 每日最大步行距离；已按真实步行路线累计并执行 |

响应固定包含：`days[].travel_date`、`days[].items[]`（含 `opening_known`）、`days[].estimated_cost`、
`total_estimated_cost`、`budget_total`、`budget_difference`、`over_budget`、
`status`（`ok` / `partial` / `empty`）、`weather_known`、`notes`、`source`。

规则：

- 排不出行程不是 HTTP 错误：城市不存在或没有 POI 返回 404；候选不足或全部闭馆返回 200，并用 `status` 表达。
- 预算是软约束：先逐日安排，再累计全程费用；超预算只降低费用评价并给出负差额，不删除方案。
- 天气未知时 `weather_known=false`，天气敏感景点按中性分参与评分，`notes` 明确写“未按天气优化”。
- 路线/步行距离已接入；仍无法确认的开放时间、天气等约束必须在 `notes` 中列出，不能静默当作已满足；`opening_known=false` 表示开放时间待用户核实。

## 4. 数据与技术方案

### 数据原则

- 优先评估地图服务获取地点、地图、路线和天气；服务权限、配额、费用、数据规则及天气日期覆盖均须在接入前核实。
- 景点开放时间、票价和临时公告优先参考景点或博物馆等官方信息，只补充实际需要的重点地点。
- 官方数据采集采用**白名单适配器 + 人工维护**：只在允许的站点、限速抓取，不登录、不绕过验证码、不调用未授权内部接口、不批量复制图片；逐站检查 robots 和服务条款，无法确认就转人工录入或标未知。
- 采集只写数据库，运行时规划不依赖实时官网抓取；每条记录保留来源、采集时间、核验时间、状态、原始文本和可信度。
- 室内/户外属性按高德分类/typecode 建立映射并支持人工覆盖；不把高德 `indoor_map` 当作“室内景点”字段。
- 门票不能由高德 `biz_ext.cost` 代替（2026-10-30 北京 526 个景点样本覆盖 0/526）；重点景点以官方票价为准，其他标未知或估算。
- 不要求首版覆盖所有城市和所有景点，也不建设全国性通用爬虫。无法合规、稳定取得的数据标为未知或待确认。
- 记录关键数据来源、更新时间和可靠程度；不把估算或 Mock Data 描述成真实数据。
- 中国境内坐标须注意高德 GCJ-02 与数据库 WGS84 坐标系转换。

### 外部服务验证记录（2026-10-30 实测）

使用当前 `AMAP_API_KEY`（Web 服务 Key）实测，结果如下：

- **路线**：8/8 接口可用（地理编码、逆地理编码、POI 搜索、驾车、步行、公交、骑行、距离测量）。故宫→国博步行 2316 m / 1853 s，含 polyline；公交 2411 s、票价 2 元、步行 1340 m；驾车、骑行可用。
- **POI**：北京去重 526 条；`opentime2` 覆盖 83.5%，可解析 76.2%；`biz_ext.cost` 覆盖 **0/526**；上海、杭州、福州各抽样 25 条，开放时间覆盖 23/25、25/25、22/25。
- **天气**：北京/上海/杭州/福州均返回 4 个 casts（当天+3 天）；接口只有 adcode，没有日期参数，超出范围不可得。
- **静态地图**：当前 Web 服务 Key 可返回 PNG，支持标注和折线，可用于“1→2→3”顺序图，无需 JS API Key。
- **配额**（[高德服务升级页](https://developer.amap.com/upgrade#price)）：个人认证约基础 LBS 15 万次/月、搜索 5000 次/月、天气 5000 次/月；企业认证更高。实际额度与 QPS 以控制台为准。
- **结论**：路线、近 4 天天气、POI、城市编码和静态地图可用；票价、室内外属性、节假日开放时间不能依赖高德，必须官方核验或标未知。早期探测记录不再作为当前可用性的依据。

参考：[路径规划](https://lbs.amap.com/api/webservice/guide/api/direction)、[天气查询](https://lbs.amap.com/api/webservice/guide/api-advanced/weatherinfo)、[静态地图](https://lbs.amap.com/api/webservice/guide/api/staticmaps)、[和风天气每日预报](https://dev.qweather.com/docs/api/weather/weather-daily-forecast/)（仅作后续备选，未接入）。

## 7. 主要风险与替代方案

| 风险 | 处理与降级 |
|---|---|
| 官网不允许采集或页面变化频繁 | 白名单 + 逐站条款检查 + 人工兜底；采集只写数据库，不运行时抓取；缺失标未知 |
| 票价、开放时间难以确认 | 仅维护重点景点官方资料；其他标未知/估算；不把估算写成官方价 |
| 天气服务只覆盖近几天 | 近 4 天用真实预报，超出标未知；提供不依赖天气的基础安排，不声称已优化 |
| 静态地图 Key 或服务协议受限 | 后端代理/缓存，前端不接触 Key；失败时用顺序列表兜底 |
| 高德配额、QPS 不足 | 路线/天气/静态图缓存，减少重复调用；限制方案数量，必要时降级 |
| 路线失败或数据缺口 | 标记 `failed`/`unknown`，不用直线距离冒充；允许部分行程或空行程 |
| 版本迁移和旧数据 | 先修正单城市与日期口径，再保存版本；旧数据保留只读，不覆盖 |
| 数据量超出进度 | 福州、北京各 15–20 个即可；上海不作为验收项；重点景点核验，其余用高德并标未知 |
| 项目时间不足 | 先完成福州单城闭环，再扩北京/上海；减少方案种类，推迟高级功能 |

任何降级都必须在界面说明；宁可减少覆盖，也不输出看起来可信但实际未经验证的信息。

## 8. 项目原则

1. 真实数据、估算和 Mock Data 明确区分。
2. 外部服务接入前核实权限、限制和使用规则。
3. 硬约束与软目标分开处理；总预算是软约束。
4. 天气必须实际影响首版规划，未知天气不得猜测。
5. 不收集规划所需之外的个人信息，不传播未授权内容。
6. 先完成单城市规划闭环，再评估跨城规划、动态重规划或 AI。
7. 官网数据采用白名单受控采集 + 人工核验，采集与运行解耦，不建通用爬虫。
8. 地图只做每日 1→2→3 顺序展示，不做导航和交互地图。
