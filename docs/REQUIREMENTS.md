# TravelMind 智能旅行规划系统 — 需求规格说明（Phase 0）

> 本文档是项目的**需求基线**。后续任何阶段的设计、实现与偏离，都以本文档为准绳。
> 来源：Phase 0 需求分析与项目设计阶段产出。内容保持原样，不做增删。

下面这份说明作为后续所有阶段的基线。它不涉及后端或前端代码实现，而是把"业务、数据、约束、架构边界、技术可行性"先明确下来，确保后续开发按真实软件工程流程推进。

---

## 1. 项目背景

随着旅行需求从"攻略查询"转向"智能决策"，用户不再满足于简单的景点推荐，而是希望系统在真实约束条件下自动生成一套可执行的旅行方案。

当前存在的典型问题包括：

- 用户只能手工搜集景点、票价、交通、酒店和天气信息，效率低
- 旅行行程往往受时间、预算、步行距离、兴趣偏好和交通方式影响很大
- 旅游方案常常依赖经验或单一大模型输出，缺乏真实数据支撑
- 景点开放时间、节假日、交通实时变化和预算控制常常被忽略
- 同一目的地的不同用户需求差异很大，但现有产品难以做个性化路线规划

TravelMind 的目标，是构建一个"基于真实数据 + 用户约束 + 多目标优化"的旅行规划平台。它不是生成一篇旅游攻略，而是生成"可执行、可预算、可优化、可解释"的旅行计划。

---

## 2. 项目目标

### 2.1 总体目标

构建一个可用于国内外旅行场景的智能旅行规划系统，支持：

- 用户输入旅行约束
- 获取真实景点、交通、天气、住宿和活动数据
- 基于约束和偏好筛选候选对象
- 计算路线、时间窗口和费用
- 自动生成多个不同偏好的方案
- 支持动态重规划和后期 AI 解释

### 2.2 核心业务目标

- 自动生成一套完整旅行方案
- 满足用户约束条件（预算、时间、步行距离、交通偏好等）
- 兼顾兴趣匹配度和旅行舒适度
- 输出多个方案以便用户比较
- 为后续扩展留出动态规划和 AI 对话空间

### 2.3 项目价值

- 提升旅行规划效率
- 降低用户决策成本
- 提高方案合理性和可执行性
- 为后续城市/目的地扩展打基础
- 让系统从"信息聚合"走向"智能决策辅助"

## 3. 用户角色

### 3.1 普通用户

典型使用者，具备以下行为：

- 输入旅行目的地、日期、预算、人数和偏好
- 查看推荐方案
- 比较不同方案的费用、路线和兴趣匹配度
- 调整约束条件后重新生成方案

### 3.2 旅行管理员 / 平台运营

负责：

- 维护城市、景点、酒店和活动数据
- 审核抓取数据质量
- 处理异常数据和数据源状态
- 观察规划结果质量和系统异常

### 3.3 数据维护人员

负责：

- 对接官方 API
- 维护爬虫任务
- 检查数据清洗与标准化质量
- 分析数据可信度和更新频率

### 3.4 系统开发 / 运维人员

负责：

- 服务部署
- API 稳定性
- 数据库索引与空间查询优化
- 监控和日志

## 5. 非功能需求

### 5.1 性能需求

- 单次规划请求在合理时间内返回结果
- 对新用户，规划过程应及时反馈进度
- 数据查询特别是 POI 和路线查询应尽量低延迟

### 5.2 可用性需求

- 前端界面清晰、操作简单
- 所有关键状态可见
- 方案结果可比较、可筛选、可修改

### 5.3 可维护性需求

- 模块职责清晰
- 数据层、算法层、服务层、接口层分离
- 各阶段独立开发和测试
- 关键数据字段统一命名和标准化

### 5.4 数据一致性需求

- 数据必须可追踪来源
- 每条重要记录都保留来源和更新时间
- 景点价格、开放时间、天气等应更新不混淆

### 5.5 安全需求

- 不直接暴露敏感 API Key
- 需要对抓取和外部服务访问做权限控制
- 守住合法抓取边界，避免违规爬取

### 5.6 扩展性需求

- 后续支持更多城市、更多景区、更多交通模式
- 规划算法可逐步升级从规则评分到 OR-Tools 和启发式优化
- 地图模块和数据采集模块必须独立扩展

## 6. 系统边界

### 6.1 系统在范围内

- 用户旅行需求录入
- 数据采集与标准化
- 旅行景点、交通、酒店、天气的基本查询
- 自动生成行程
- 方案比较与可视化
- 地图展示
- 费用估算
- 缺少数据时使用明确标记的 Mock Data

### 6.2 系统不在范围内

- 线上支付
- 实时机票/酒店预订
- 社交与攻略发布
- 用户评论和评分系统
- 跨境全部交通网络的全量覆盖
- 大规模全国实时爬虫
- 过度依赖大模型直接编造旅行计划

### 6.3 系统边界原则

- 数据源必须可审计
- 规划计算必须有明确规则和评分模型
- **AI 仅作为自然语言理解和解释层，不替代规划计算器**

## 8. 核心业务流程

### 8.1 核心流程

```text
用户提交旅行需求
   ↓
需求结构化
   ↓
候选 POI 检索
   ↓
数据整合
   ↓
过滤与评分
   ↓
路线与时间计算
   ↓
费用估算
   ↓
多方案生成
   ↓
前端展示
   ↓
用户确认 / 调整
   ↓
重规划
```

### 8.2 典型业务流程示意

- 用户输入：福州 → 北京，5 天，2 人，预算 8000，兴趣偏好为历史文化/美食等
- 系统解析需求
- 查询北京景点、气候、酒店和交通数据
- 过滤不满足开放时间、预算和步行距离的候选
- 计算景点间距离与交通时间
- 组合出一日的游玩顺序
- 生成多方案
- 用户查看：综合最优 / 最省钱 / 最舒适 / 最省时
- 用户可调整预算、兴趣或天数再生成

### 8.3 关键执行节点

1. 需求解析
2. 数据采集
3. 数据规范化
4. 候选筛选
5. 行程优化
6. 方案生成
7. 结果展示
8. 调整和重规划

## 9. 用例分析

### 9.1 用例：创建旅行计划

- 参与者：普通用户
- 触发条件：用户填写旅行参数
- 基本流程：
  1. 用户输入出发地/目的地/日期/人数/预算/偏好
  2. 系统校验字段合法性
  3. 生成旅行需求对象
  4. 启动规划任务
  5. 返回规划结果页

### 9.2 用例：查看方案并比较

- 参与者：普通用户
- 目的：查看多方案对比
- 基本流程：
  1. 查看方案列表
  2. 比较综合评分、费用、时长、舒适度
  3. 选择某方案查看详情

### 9.3 用例：重规划

- 参与者：普通用户
- 目的：在已有方案基础上调整约束
- 基本流程：
  1. 修改预算或偏好
  2. 提交重规划
  3. 重新计算候选景点和路线
  4. 更新方案列表

### 9.4 用例：查看地图路线

- 参与者：普通用户
- 目的：查看景点间路径和每日分段路线
- 基本流程：
  1. 选择某一天
  2. 显示景点顺序
  3. 展示路线和距离
  4. 查看交通方式和步行信息

### 9.5 用例：数据更新

- 参与者：数据维护人员
- 目的：更新景点、门票和天气数据
- 基本流程：
  1. 拉取新数据
  2. 清洗与标准化
  3. 更新数据库
  4. 记录 source / confidence / timestamp

### 9.6 用例：动态重规划

- 参与者：系统 + 用户
- 目的：天气变化或景点关闭时重算剩余行程
- 基本流程：
  1. 检测天气变化/景点关闭
  2. 识别受影响行程
  3. 重新筛选替代 POI
  4. 更新后续计划

## 10. 数据流分析

### 10.1 数据输入

- 用户输入
- 第三方 API
- 网页抓取结果
- 配置参数和规则

### 10.2 数据处理链路

```text
用户输入 / 外部数据
   ↓
数据采集模块 → 解析 → 清洗/标准化 → 存储
   ↓
规划引擎 → 评分与路线优化
   ↓
方案输出 → 用户展示
```

### 10.3 关键数据流

**1. 用户需求流**

- 用户输入参数 → 结构化需求模型 → 规划请求

**2. 地点与交通流**

- POI 数据 → 筛选 → 路线计算 → 每日安排

**3. 费用流**

- 门票、酒店、交通、餐饮 → 汇总 → 总费用与人均费用

**4. 天气流**

- 气象数据 → 适宜性评估 → 影响路线和替代选择

**5. 数据来源流**

- source / source_url / updated_at / crawl_time / confidence → 数据审计链路

### 10.4 数据处理原则

- 强制保留数据来源
- 所有重要字段必须可回溯
- Mock Data 必须明示为 Mock，不得冒充真实数据

## 11. 核心业务规则

### 11.1 旅行约束规则

- 预算不能为负
- 旅行日期必须合法
- 人数至少为 1
- 每天工作时间必须在允许范围内
- 景点开放时间必须满足当日访问窗口

### 11.2 景点筛选规则

- 只保留目的地城市内或可访问区域内的 POI
- 过滤在旅行日期不开放的景点
- 过滤超出预算/步行限制的候选对象
- 过滤与用户兴趣不匹配程度过低的 POI

### 11.3 路线规则

- 景点顺序必须尽量折减总距离
- 对于晚上较晚的安排，需避免过远的跨城交通
- 步行距离与用户阈值保持一致
- 优先考虑公共交通和低疲劳路线

### 11.4 费用规则

- 费用按人/天/总额分项计算
- 酒店选择应结合人数和预算
- 交通和门票价格必须来自真实数据或明确标注 Mock

### 11.5 方案输出规则

- 至少输出多个方案类型
- 每个方案必须标明评分、费用与适用人群
- 结果必须有解释性

### 11.6 数据可信度规则

- 官方数据优先
- API 数据优先于抓取数据
- 抓取结果需保留来源和可信度评分
- 低可信度数据不能直接决定关键决策

## 12. 风险分析

### 12.1 数据风险

- 第三方 API 可能限制调用频率
- 网页页面结构变化导致抓取失败
- 天气和交通数据存在延迟
- 同一 POI 的价格和开放时间可能不一致

### 12.2 算法风险

- 规则评分模型容易忽略全局最优解
- 复杂路线优化可能带来较高计算成本
- 时间窗口约束处理不当会导致路线不可执行

### 12.3 产品风险

- 用户对"智能推荐"期望过高，可能以为系统掌握了所有真实库存和实时政策
- 若数据不足，输出方案可能看起来"合理但不真实"

### 12.4 合法性风险

- 抓取数据可能触碰网站条款
- 商业旅游网站、部分官方数据接口可能有使用限制或付费限制

### 12.5 运维风险

- 地图和 API 服务的故障会影响规划结果
- 大量数据同时查询会导致服务性能下降

## 13. 技术可行性分析

### 13.1 后端：FastAPI + Python

可行性很高，原因：

- API 开发效率高，适合 REST 接口
- Web 抓取生态成熟
- 数据处理与算法生态丰富
- 与 SQLAlchemy、Pydantic、httpx、Playwright 等工具结合友好
- 更适合旅行规划和数据分析场景

### 13.2 数据库：PostgreSQL + PostGIS

适合原因：

- 需要处理经纬度、距离、附近搜索、路线空间查询
- PostGIS 支持功能强大的地理计算
- 适合 POI、交通和地图相关业务

### 13.3 前端：Vue 3 + TypeScript + Vite + Element Plus

适合原因：

- Vue 3 生态成熟
- TypeScript 提升可维护性
- Vite 开发效率高
- Element Plus 能快速完成 UI
- 适合做旅行搜索、结果展示和地图交互

### 13.4 多源数据整合

- 官方 API 与公开数据可构成稳定基础
- 网页抓取用于补齐缺失字段
- 结构化数据 + 标准化库可提升数据质量

### 13.5 规划算法可分阶段落地

- 第一阶段：规则 + 加权评分
- 第二阶段：贪心算法
- 第三阶段：时间窗口约束
- 第四阶段：TSP / VRP
- 第五阶段：OR-Tools
- 第六阶段：遗传算法 / 模拟退火

这符合"先保证正确，再加复杂度"的工程原则。

## 14. 数据来源可行性分析

### 14.1 中国区域数据源

- **高德地图 API**
  - 优势：地理编码、路线规划、POI、地图展示能力强
  - 适用场景：起点/终点、路线时间、附近 POI、交通方式
- **景区官网 / 博物馆官网**
  - 优势：门票、开放时间、临时公告信息可靠
  - 适用场景：景点真实数据获取
- **城市旅游局和政府网站**
  - 优势：活动、公告、节假日信息
- **天气 API**
  - 优势：适合旅游天气和风险判断
- 适用策略：API 优先，抓取补充

### 14.2 国际区域数据源

- **OpenStreetMap** —— 地理信息、POI 与道路数据
- **Open-Meteo** —— 天气预报
- **Amadeus** —— 航班、酒店和旅行相关服务
- **地方官方旅游网站** —— 补充活动及开放时间

### 14.3 网页抓取策略

优先抓取：

- 官方景区网站
- 城市旅游局
- 博物馆官网
- 政府公开公告
- 活动官网

不优先抓取：

- 大型商业旅游网站的高强度、侵入式抓取
- 依赖登录、验证码、反爬机制的站点

### 14.4 数据可信度模型

每条关键数据至少记录：

- source
- source_url
- crawl_time
- updated_at
- confidence

如果没有真实数据，允许使用明确标注为 Mock Data 的样例数据，但必须明确说明来源不是真实数据。
